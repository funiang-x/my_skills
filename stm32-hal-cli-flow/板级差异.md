# STM32 板级差异清单

> 本文件是 [`adapter.md`](adapter.md) 第 6 项：**换芯片 / 换板子时，必须同步哪几处。**
> 格式铁律：每条给「改哪 → 判据」。**不许写"参考文档"了事**——那等于没写。

## 1. 换芯片（同厂不同型号）

| # | 改哪 | 判据 |
|---|---|---|
| 1 | 链接脚本 `*.ld` 的 MEMORY 段与段布局 | 容量数字**从 CubeMX 固件包官方 `.ld` 现读**（`~/STM32Cube/Repository/STM32Cube_FW_F4_*`），**不凭记忆、不手填** |
| 2 | 启动文件 `startup_<device>.s` | 文件名与器件一致，且被 CMake 引用到 |
| 3 | `.ioc` 芯片型号 | 用 CubeMX 打开不报型号不符 |
| 4 | `Core/Inc/board_config.h` 的器件名 / 容量 / 引脚 | `fw.py lint` 对账通过（**唯一权威判据**） |
| 5 | **清 `build/`** | 不清就会沿用旧内存布局 |

### 第 5 条为什么要单独写

`LINKER_SCRIPT` 是 CMake **CACHE** 变量。芯片名改了、链接脚本没变，**编译照样过** ——
这是**假成功**，实测踩过。换芯片后必须清 `build/`（派生脚本已自动清）。

### 判定"切换是否真生效"

**首选**：配置输出里的芯片名 + 构建日志里编的启动文件。

⚠️ **不要只看 `fw.py size` 的内存数字**：同容量芯片之间可能**逐字段完全相同**
（实测 F405RG → F407VG：官方 ld 的 ROM 1024K / RAM 128K / CCM 64K 三项一模一样，
只有 ETH 与 DCMI 两个外设不同）。**数字没变 ≠ 切换失败。**
换到 F429 才会看到 2 MB / 192 KB / QSPI 16 MB 的变化。

## 2. 换板子（同芯片，改引脚与时钟）

| 改哪 | 判据 |
|---|---|
| `Core/Inc/board_config.h` 的引脚宏 | `fw.py lint` 对账通过 |
| `.ioc` 的引脚分配（经 CubeMX 改） | 同上；**AI 改完必须让人在 CubeMX 核对确认** |
| 外设实例（哪个 USART / 哪个 SPI） | 与板级头文件一致，且 `Device/Inc/bsp_port_map.h` 同步 |
| 时钟树 | 时钟自检通过（模板里时钟不符合预期会打 `[AI_FAIL]`） |

**铁律**（见 [`framework/骨架总则.md`](../framework/骨架总则.md) §5）：
改引脚或时钟**动手前必须先问人**。AI 改完 `.ioc` 与生成代码，**人工在 CubeMX 核对确认**。

## 3. 换板子后必须重跑

```
lint → build --clean-first → sizecheck → verify
```

`verify` 是唯一能证明"新板子真跑起来"的判据（退出码 0 = 抓到 `[AI_READY]`）。
⚠️ 退出码 2 **不等于**固件有问题 —— 也可能探针没插，先跑 `fw.py env`。

## 4. 本层与骨架层的边界

上表全是要读**芯片手册 / CubeMX 仓库 / J-Link**才知道的东西 ⇒ 属适配层。
骨架层只知道一条普遍规律：「改一处必须同步它的下游」（`WORKFLOW.md` §5 的同步表）。
新芯片接入时照本文件的格式写一份自己的差异清单，**不要把 STM32 的条目抄进骨架层**。
