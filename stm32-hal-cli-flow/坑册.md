## A. 流程 / 工具链

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| A1 | `fw.py env` 报 `UnicodeEncodeError`，看起来像门禁失败 | 输出含 `⇒` 等非 GBK 字符，Windows 控制台默认 GBK | 调用前设 `PYTHONIOENCODING=utf-8` |
| A2 | skill 里引用的脚本/文档**不存在**，照做白跑 | `check_doc_links.py` 只扫 `.md`/`.txt`，**管不到 skill 文件** | 引用路径前先 `Test-Path` 核实；引用即核实 |
| A3 | `cmake --build --preset X` 非 0 退出，被当成"编译失败" | 构建目录不存在时 cmake 直接非 0，和"源码有错"同码 | 用 `fw.py build`（缺 `CMakeCache.txt` 会自动先 configure）。换芯片清了 `build/` 后尤其容易撞上 |
| A4 | `fw.py verify` 退 2，以为固件坏了 | 退 2 = 超时/无标记，**也可能是探针没插** | 先 `fw.py env` |
| A5 | 改了代码但门禁说"零告警通过"，其实有新告警 | 增量构建只重编改动过的文件 | 每个预设都要 `--clean-first` 才算零告警口径 |
| A6 | 改完 `Tools/` 检查器，门禁"变绿"了 | 检查器可能压根不报错 | 跑 `fw.py selftest`：基线全绿 + 逐条注入真违规必须报错 |

## B. 换芯片 / 内存

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| B1 | 芯片名变了、编译照样过，但行为不对 | `LINKER_SCRIPT` 是 CMake **CACHE** 变量，`build/` 不清就沿用旧内存布局 | 换芯片后清 `build/`（**假成功**，实测踩过） |
| B2 | 换芯片后 `fw.py size` 数字没变，以为没生效 | 同容量芯片内存映射可能逐字段相同（F405RG 与 F407VG 的 ROM/RAM/CCM 三项一样） | 看**配置输出的芯片名**与**构建日志里编的启动文件**，别看内存数字 |
| B3 | 段名与已有段名前缀重叠，16 KB 零值被写进 Flash | `*(.ccmram*)` 会吞掉 `.ccmrambss*`，而 `.ccmram` 是 `AT>FLASH` | 无初值大块用 `.ccmnoload` 这类不重叠的名字 |
| B4 | CCM（`0x1000_0000`）上的缓冲 DMA 摸不到 | CCM 不在 DMA 可达总线 | 显示缓冲必须留主 SRAM；可搬的是 RTOS 堆、内存池、静态任务栈 |
| B5 | `.ioc` 里没配的外设，一用就编译失败 | 其 HAL 模块宏没开（`stm32f4xx_hal_conf.h`），报 `unknown type name 'Xxx_HandleTypeDef'`（**编译期**） | 去 CubeMX 加一个该外设。**不要手改 `hal_conf.h`**（生成物，下次生成会覆盖） |

## C. 构建优化 / 对照实验

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| C1 | `--gc-sections` 没删掉文件内未引用函数 | 缺 `-ffunction-sections -fdata-sections`，GC 只能以整个 `.o` 为粒度 | 两者一起加进工具链文件的 `ARCH_FLAGS`（实测 Release 441,184 → 318,812 B，0 告警） |
| C2 | 同源代码在不同目录构建出**字节不同**的固件 | `__FILE__` 绝对路径进了固件（`vAssertCalled(__FILE__, __LINE__)` 等） | 固定路径，或加 `-ffile-prefix-map=<前缀>=.`（实测差 184 B = 路径长度差） |
| C3 | 对照实验"成功"了但几个变体 elf 字节相同 | `subprocess` 调 cmake 只给 `-B`，CMake 以**当前工作目录**为源目录 ⇒ 对副本的补丁全被忽略 | 显式传 `cwd=` 或 `-S <副本>`（一整轮实验因此全废） |
| C4 | LTO 链接失败 | LTO 分区未解析引用 + `dangerous relocation` | 本工程别用 LTO，即使 `-flto` 同时进编译与链接 |

## D. 烧录与"固件到底在不在板上"

| # | 现象 | 根因 | 处置 |
|---|---|---|---|
| D1 | `JLink verifybin xxx.bin` 必然报 `Verify failed` | 链接脚本在 `.isr_vector` 与 `.text` 间有 `ALIGN(4)` 间隙；`objcopy` 用 `0x00` 填充而 Flash 是 `0xFF`（实测 367,548 B 中仅 8 B 不同，全在 `0x188–0x18F`） | 用 RTT 的 `[AI_READY]`（`verify` 退出码），或整片 `savebin` 后按 ELF 的 LOAD 段比对 |
| D2 | `J-Link loadfile` 打印 `Skipped. Contents already match`，以为没烧 | 该消息**不可当判据**（实测两次打印该消息、实际都烧进去了） | 用**功能判别器**：改一个可观测行为，看 RTT 里对应输出出现/消失 |
| D3 | 日志看着"丢数据"，以为固件有 bug | RTT 缓冲区默认 1024 B，写快了会静默丢 | 见工程侧 `README.md` 的 RTT 说明；判故障前先排除丢数据 |
