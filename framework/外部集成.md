# 外部集成 —— 什么时候该用外部协议（含 MCP）

> 本文件是 [`骨架总则.md`](骨架总则.md) §2 的**第五份契约**。
> 它只回答一个问题：**这一步该走本地文件 + CLI，还是该接一个外部服务？**
> 具体接哪个服务、怎么配，属适配层的事。

## 1. 一条判据

> **够不到的东西才用外部协议；够得到的别绕。**

拆成两问，**两问都答"是"才接**：

| 问 | 说明 |
|---|---|
| **够不到吗？** | 目标是不是**进程外**的东西——另一个 GUI 应用、一台仪器、一个云服务？如果它只是一个本地 CLI 能跑的命令，就是"够得到" |
| **有新增能力吗？** | 接进来之后模型能做它**现在做不到**的事吗？只是把同一个命令换个调用方式 → 没有新增能力 |

**只满足第一问、不满足第二问 = 加了一层不加能力**（见 §4 的成本）。

## 2. 按环节的判据（本库现状）

| 环节 | 够不到吗 | 有新增能力吗 | 结论 |
|---|---|---|---|
| **EDA 落图 / 原理图 / PCB** | ✅ 是（嘉立创 EDA / KiCad 是**外部 GUI 应用**） | ✅ 是。直接产 `.kicad_sch` / EDA JSON 有 **坐标精度、符号库依赖、格式复杂度**三重问题；走 EDA 原生 API 由 EDA 自己处理坐标对齐与符号引用 —— 这是**本质改善**，不是换皮 | **值得接** |
| **仪器 / 探针 / 示波器 / 电源** | ✅ 是（外部硬件） | ✅ 是。读寄存器 / 设电压 / 抓波形变成结构化调用 | **值得接**，但设备动作仍守 [`骨架总则.md`](骨架总则.md) §5 的边界（先问人） |
| **构建 / 烧录 / 调试** | ❌ 不是（`Tools/fw.py` 就是本地 CLI） | ❌ 没有。包一层只是把 `python Tools/fw.py build` 换成一次工具调用 | **不接** |
| **skill 路由**（该用哪个 skill） | ❌ 不是（是本地文本） | ❌ 没有。而且会把"任何能读文件的 agent 都能用"降级成"只有支持该协议的客户端能用" | **明确不接** |

**第 4 行是这套库的根**：路由必须是**纯文本 + 显式声明**，任何 agent 都读得懂。
把它做成外部服务的工具，等于用"平台特性"换掉"跨端一致"—— 那正是本库要解决的问题。

## 3. 成本要算清楚（外部协议不是免费的）

| 成本 | 说明 |
|---|---|
| **常驻上下文** | 工具定义与服务端说明在**没被调用时也占**上下文；还有 KV-cache 命中率的副作用。一个客户端里已经有 skill 目录占着一份，再接服务就是第二份 |
| **常驻进程** | 服务端要装、要起、要更新、要判活（EDA 的 daemon 还得防它顶掉你的 skill 接线，见 `ROUTE.md` §2.7） |
| **第二处真相源** | 服务端的能力描述与你的 skill 规程会各说各的，又成了一份要维护的复述 |
| **跨端不一** | 各家客户端对同一协议的支持面不同；接了就得接受"换个客户端这步可能没有" |

## 4. 接进来的硬要求（四条，缺一不算合格）

1. **必须写回退路径**：没有该服务时，那一步要能退回**人可读的产物**
   （EDA 的回退就是"结构化连接表"，已有先例）。
2. **必须在 ROUTE 里登记**：它是哪个任务类型的手段、属于哪一层；不登记等于暗路。
3. **不许成为主干前置**：主干（判阶段 / 路由 / 门禁 / 工程状态）跑起来**不需要它**。
4. **设备动作要人确认**：通过外部协议下发的烧录 / 擦除 / 上电类操作，
   与本地 CLI 同一把尺子——**先问人**。

## 5. 现状（本机实测，2026-10）

| 项 | 状态 |
|---|---|
| [`hardware-solution`](../hardware-solution/SKILL.md) 的 EDA 两条路径 | **已在用 MCP**（KiCad / 立创 EDA），并带"没有就回退连接表"的规则 |
| 本机已装的 EDA MCP 服务 | **都没装**（`jlceda-mcp` / `kicad-mcp` / `mcp-kicad-sch-api` 均未安装）⇒ 当前实际走的是**回退路径** |
| 客户端支持 | 至少 DSH / Trae / Codex / CodeBuddy / ZCode 的工具链里都有 MCP 相关能力（各自配置方式不同） |

### ⚠️ 没验证的部分（别照抄我编的配置）

**没验证**：DSH 里写 MCP 服务器的**具体配置语法**。

**已验证**：DSH 有专门的 MCP 客户端插件（`@deepseek-ai/dsh-mcp-client`，含工具发现、
服务端说明、token 影响、已知限制的设计笔记）；配置键名是 `mcpServers`；
传输类型含 `stdio` / `http` / `sse`；配置层是 profile 的 patch 层
（`~/.dsh/profiles/<名>/cordis.patch.yml`，而 `cordis.yml` 顶部写着"改 patch 文件"）。

**结论**：接的时候**以此客户端自己的 MCP 面板／文档为准**，不要照抄本文档里的臆测语法。
配完把**实际可用的那段**回写进本文件 §5 —— 那才是能信的样板。
