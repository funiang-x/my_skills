# 工程契约 —— 一个工程要能回答哪 6 件事

> 本库**不提供门禁实现**，只定义门禁必须能回答什么。
> 实现放工程侧（STM32 用 `Tools/fw.py`），因为命令里全是芯片与探针的细节，属于适配层。
>
> 本文件是 [`骨架总则.md`](骨架总则.md) §2 的「工程契约」，也是 [`适配层契约.md`](适配层契约.md) §1 第 4 项。

## 1. 六件事（缺一件 = 这个工程不能开工）

| # | 门禁 | 拦什么 | 通过判据 | STM32 实现 |
|---|---|---|---|---|
| 1 | **体检** | 工具链 / 依赖源码 / 探针 / 各预设 | 退 0 且列出实际路径 | `fw.py env` |
| 2 | **零告警构建** | `warning` + `error` 总数 > 0 | `--clean-first` 后总数为 **0** | `fw.py build --clean-first` |
| 3 | **脱硬件测试** | 核心逻辑只能上板才验得动 | 退 0，且**不需要板子** | `fw.py test` |
| 4 | **配置对账** | `.ioc` 与 `board_config.h` 双真相源漂移 | 退 0（无确定性矛盾） | `fw.py lint` |
| 5 | **体积预算** | Flash / RAM 超上限 | 退 0 | `fw.py sizecheck` |
| 6 | **门禁自检** | 检查器自己是假的（永远报错 / 什么都不做） | 基线全绿 + 负向用例逐条报错 | `fw.py selftest` |

**为什么第 6 件必须存在**：前 5 件都是"检查器说没事"，而检查器可能是坏的。
只有注入真违规、看它**必须报错**，才能证明前 5 件可信。少了它，整套门禁退化成形式。

## 2. 两项结构要求

| 要求 | 判据 |
|---|---|
| **板级单一真相源** | 器件名与内存容量只在一处（STM32 在 `Core/Inc/board_config.h`）；引脚分配只有一处；全仓搜不到第二处重复定义 |
| **四层目录各带 README** | 业务 / 设备 / 公共 / 任务四层各有 `README.md`，写清"这层放什么、不许放什么" |

## 3. 不许做的事（会说话的一票否决）

- **为了让门禁变绿而放宽门禁**：调高体积上限、加 `-Wno-*` 消警告、把负向用例删掉。
  要调先走规范提案流程，改完门禁自检必须仍然证明它有效。
- **把退出码 2 当成"固件有问题"**：可能就是探针没插。报故障前先跑体检（第 1 件）。
- **体积口径各写各的**：唯一来源是工程内的体积脚本，别的文档只能引用不能复述。

## 4. AI 调用门禁的固定约定

```
$env:PYTHONIOENCODING='utf-8'      # Windows：必须先设
python Tools/fw.py <子命令>
```

**为什么**：`fw.py` 输出含 `⇒` 等非 GBK 字符，GBK 控制台下会抛
`UnicodeEncodeError` 直接崩——**看起来像"门禁失败"，其实是编码问题**。
这个根因不写在代码里就没人知道，所以它是契约的一部分，不是可选提示。

退出码一律以脚本为准；**要结论就读退出码，不要读输出里的措辞**。

## 5. 接口只有三个

契约实现方（适配层）只需要暴露三样东西，别的一律不管：

1. **一条命令**：能一次跑完 6 件事（STM32 走 `verify` 或逐个跑）
2. **一张判据表**：6 件事各自"怎么算过"写进适配层文档
3. **一份退出码约定**：每个非 0 码代表哪一类失败

工程内部怎么实现（几个脚本、什么语言、目录怎么排）本契约不管。
