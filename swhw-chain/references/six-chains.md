# 主干与五类附件 —— 填写要求、反例

> 原来的"六条链"在这里重组为：**数据链 = 主干**（链节本身），
> 其余五条 = **挂在主干上的附件**。为什么：分类回答"有哪些"，链回答"谁扣着谁、断在哪"。
> 字段定义与断链判据见 [`chain-model.md`](chain-model.md)。

---

## 主干 = 链节（原「数据链」）

**回答**：这个工程的**那条通路**，逐节往下走。

| 列 | 必填 | 说明 |
|---|---|---|
| ID | ✅ | `L01`…`Lnn`，**编号即顺序** |
| 做什么 | ✅ | 动词开头，一句话 |
| 上游 / 下游 | ✅ | 相邻节 ID；首/末节写 `—`。**互指必须一致** |
| 载体 | ✅ | 变量 / 寄存器 / 节点名 / 文件。**写具体名字** |
| 单位 | ✅ | 每节都要写；无量的写 `—` |
| 证据 | ✅ | 路径 + 行号 / 器件位号 |

**填写要求**
- **先定主干，再挂附件。** 主干选错，后面全废。
- **单位是主干的灵魂**：写"码值 → mV → mV(源端口径)"比写"数据传递"有用一百倍。
- 凡是**量纲/口径变了一次**的地方，单独标出来（例：`/g` 之后从"ADC 端 mV"变成"源端 mV"）。
- 内存落点（哪个数组在哪个 RAM 段）也要写 —— 这类约束一破就是**静默失效**。

**反例**
- ❌ "ADC 采集后送 DSP 处理，结果送屏幕显示" —— 四节并成一句，什么都没说。
- ❌ 主干写成并列的两条（"信号通路" + "控制通路"）—— 那是两份报告。

## 附件 R · 需求

**回答**：规格里的每个数字，**谁保证它**。

| 列 | 必填 | 说明 |
|---|---|---|
| ID | ✅ | `R1`… |
| 内容 | ✅ | 需求原文（**引原话**，不转述） |
| **挂在链节** | ✅ | 哪些链节共同保证它（可多个） |
| 判据 | ✅ | 变成"怎么量、量到多少算过"。**带单位与容差** |
| 证据 | ✅ | 路径 + 行号 / 器件位号 + 参数 |
| 强度 | ✅ | 已核 / 推导 / 待确认 |

**最容易漏的**：需求里那些"没写出来但必须成立"的**隐含前提**（例：题面说 10k~500kHz，
隐含"ADC 采样率 ≥ 1MSPS"）。隐含前提要单列一条 `R`，并标出"由谁保证"。

**反例**：❌ `挂在链节` 留空 ⇒ `chain.py` 会报"**没人保证这个需求**"。这是本模型最严重的失败。

---

## 附件 F · 功能

**回答**：功能落在**哪几节**。

| 列 | 必填 | 说明 |
|---|---|---|
| ID | ✅ | `F1`… |
| 内容 | ✅ | 功能一句话 |
| 落在链节 | ✅ | 这功能体现在哪些链节 |
| 证据 | ✅ | 路径 + 行号 |

**填写要求**
- 同时写**分层规则**（谁只能向下调）与**唯一的跨层例外**（全工程只应有一处）。
- 把"**谁不调谁**"也写出来（例：纯算法层不 include 硬件头、不读配置头，参数靠注入）。
  这条比"谁调谁"更能说明设计意图 —— 可以放进本表的"内容"列，或写成附件 `I`。

---

## 附件 I · 交互

**回答**：硬件 ↔ 固件怎么对上；**改了要连带什么**。

| 列 | 必填 | 说明 |
|---|---|---|
| ID | ✅ | `I1`… |
| 硬件实体 | ✅ | 器件位号 + 页名（或外设名） |
| 固件实体 | ✅ | `bsp_*.c` / 宏 / 回调 |
| 落在链节 | ✅ | 这一节用的是哪个外设 |
| **改了要连带什么** | ✅ | **本表存在的理由** |
| 证据 | ✅ | 网表节点名 + 代码路径 |

**填写要求**：引脚事实写**两个来源**（网表节点 + 代码宏），两者对上才叫"核过"；
对不上就是附件 `K` 的一条。

---

## 附件 J · 判据

**回答**：守着哪一节；**判错什么样**。

| 列 | 必填 | 说明 |
|---|---|---|
| ID | ✅ | `J1`… |
| 判据 | ✅ | 判断的**表达式**，不是"检查一下" |
| 守在链节 | ✅ | 这一节的正确性由它把守 |
| **判错症状** | ✅ | **最重要**：判错会让人往哪个错方向查 |
| 失败语义 | ✅ | 停机 / 降级 / 跳过本节 / 只告警 |
| 证据 | ✅ | 路径 + 行号 |

**填写要求**
- 判据强度要匹配能确定的事实：「读得到」⇒ 通路存在（可用）；「等于某值」⇒
  只有当那个值由硬件保证时才可用。把这条写成一句放进报告。
- 必填一类"**静默失效守卫**"（不报错但结果全错，例：DMA 缓冲落在不可访问的 RAM 段 ⇒ 采集恒 0）。
  这类行最值钱。

---

## 附件 K · 风险 / 冲突

**回答**：哪一节有隐患；一手与文档在哪冲突。

| 列 | 必填 | 说明 |
|---|---|---|
| ID | ✅ | `K1`… |
| 结论 | ✅ | 一句话 |
| 挂在链节 | ✅ | 风险落在哪一节 |
| 强度 | ✅ | 已核 / 推导 / 待确认 |
| 依据 | ✅ | 路径 + 行号 / 脚本名 / 命令 |

**冲突登记**（一手 vs 文档）写成一段，`[冲突]` 开头：

```
[冲突] <文档路径:行> 说「<原话>」
  一手：<文件:行 / 命令输出 / 网表节点>
  影响面：<会不会真的坏；能量化就写数>
  处置：<改文档 / 改实现 / 挂待确认>
```

**填写要求**：每条"待确认"必须有"**缺什么才能确认**"。
已经量化过影响面的，把数字写进"影响面" —— 量化过的待确认，价值远高于没量化的。
